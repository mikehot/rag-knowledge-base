# Case Study：从 RAG Demo 到可治理、可度量的企业知识库

> 使用合成样例和本地环境验证，不代表真实客户上线，也不构成准确率、SLA 或 ROI 承诺。最后更新：2026-10-13。

## 1. 问题

一个能“上传文档、问答”的 RAG Demo 做起来不难，但企业真正要问的是：

- 员工能不能只看到自己有权看的资料？
- 答案从哪来？模型会不会编造出处？
- 资料里没有的内容会不会乱答？
- 文档更新失败、模型服务宕机时会怎样？
- 怎么证明它答得好、够快、成本可控？

## 2. 目标

建立一个可以运行、解释、评测、部署和交接的闭环：

> 管理员上传文档 → 持久化索引 → 员工按权限提问 → 后端生成可校验的引用 → 记录审计、延迟、Token、反馈 → 用版本化评测集复核质量。

## 开发方式

实现代码主要由 AI 编码代理（OpenAI Codex、Claude Code）编写。本人负责需求与范围、架构和技术取舍、评测设计、代码评审、验收与发布决策。第 5 节的关键判断就来自这种工作方式：代理负责执行，人负责决定做什么、何时停，以及怎样验证结论。

## 3. 方案

- **权限在检索时生效。** tenant、部门、角色、知识库成员和文档 ACL 都写在向量检索的 SQL 里，未授权内容不会进入模型上下文。
- **引用归后端所有。** 模型只返回答案、`found`、`grounded` 和片段编号；后端校验 JSON Schema 和编号范围后生成出处。任何不合规的输出都 fail-closed，转人工。
- **索引可恢复。** 持久化任务队列支持幂等、重试和重启恢复。chunk 只在全部 Embedding 成功后才在同一事务中切换，所以重建失败时旧版本继续可用。
- **可观测。** 提供 requestId、分段耗时、失败分类、Token 与估算成本指标、审计查询、用户反馈，以及受保护的检索诊断。
- **模型输出有防护。** 资料与问题按不可信数据处理，放在由服务端密钥派生的边界内；回显边界或带出资料中没有的链接的回答转人工；后端还检查被引用的分块是否真的支撑答案，不支撑时改引真正支撑的分块。
- **Embedding 可切换。** 每个分块记录生成它的模型和维度，检索只比较当前模型的向量；切换是一次带进度端点的重建。
- **Agent 有边界。** 3 个只读 Tool 和无状态 MCP 适配层复用同一套身份、ACL、调用预算和审计；不开放写操作。
- **技术选型。** Java/Spring Boot 负责业务、事务和权限，PostgreSQL + pgvector 统一存放业务数据与向量，Python 只用于评测。

架构图见 [ARCHITECTURE.md](ARCHITECTURE.md)，关键设计决策见 [PORTFOLIO.md](../PORTFOLIO.md#三个关键设计决策)。

## 4. 结果

| 维度 | 证据 |
|---|---|
| 权限 | 授权→可答、撤权→拒答（撤权后模型根本不会被调用）都有 PostgreSQL 集成测试；每次权限变更都写入审计（谁、何时、改了什么），与变更同事务提交；全新 clone 上用 curl 实测；所有评测运行 ACL 泄漏均为 0 |
| 可靠性 | 模型服务故障时返回稳定错误码；索引任务 3 次失败后可人工重试恢复；重建失败期间旧版本照常回答（有集成测试和实机复测） |
| 工程质量 | 后端 182 个测试（含 Testcontainers 集成测试），评测 Python 测试 30 个，CI 通过；备份恢复演练通过；MCP 只读冒烟检查 16/16；Android 真机完成管理员 ACL 与索引任务验收 |
| 可复现 | 全新 clone 按 README 逐字执行即可跑通，本机已有缓存时从 clone 到首个带引用回答不到 1 分钟 |
| 质量 | 本地 Gemma + bge-m3 + `AI_TEMPERATURE=0`：answer-quality 连续 8 轮每轮 11/12，**通过**自定的质量门；golden 19/20；stress 8/8。**默认配置（nomic）仍不通过**（8–10/12）。真实语料 corpus-v1（28 份文档、57 题）：可答题 44/45、拒答 12/12、ACL 泄漏 0；同配置在不同运行间波动 41–44/45。云端对照（DeepSeek flash，Embedding 仍在本地）：answer-quality 10/10/10，中位延迟约 1–1.6 秒，按官方价格估算每千次问答不到 $1。数字的口径和局限见 [PORTFOLIO.md](../PORTFOLIO.md) **注意**：这些是 2026-10-13 的测量；2026-10-14 在全新环境复测同配置的 corpus-v2 得到 38/45，重启并重载模型后 39/45（前一天 43/45，检索指标不变；落差主要是回答措辞撞上字面评分，措辞变化的原因未查明），质量门通过与否尚未在新环境重跑。 |

## 5. 过程中的关键判断

1. **结论可以是负的，而且敢把"试过但没用"的东西摆出来。** Hybrid Search（Keyword-RRF）、Reranking（候选多样性重排）、相邻块扩展、4 种切块大小、按标题切块，全部在真实语料（28 文档/57 题）和固定配置下跟默认 Vector 检索对比过。结果：Hybrid Search 18/45（明显更差，−7）、Reranking 23/45（−2），都没打赢默认的 25/45；300/60 切块修好了两道题并通过了 answer-quality 门槛，但 golden 和 stress 同时退步。按事先定好的规则，默认配置一项都没改，报告全部保留，包括失败的那些。
2. **知道什么时候停。** 语料只有 7 份文档时，Top-5 已经覆盖一半以上的 chunk，同配置两次运行就能差 ±2 分。继续在这上面调检索没有意义，所以把检索优化推迟到真实规模的语料上再做。
3. **演练比自测更能发现问题。** 从全新 clone 只按 README 操作，找到了 8 处文档缺口，还找到 1 个真实缺陷：检索只认 `READY` 状态，导致一次重建失败就会让文档下线。当天修复，并补上一个“修复前失败、修复后通过”的集成测试。
4. **实测才知道兼容性。** 接入 DeepSeek 时发现，它拒绝严格的 `json_schema` 输出格式。于是把输出格式做成配置项，并保持后端的完整校验不变。换用更强的模型后，只剩检索导致的失败，这说明下一步该优化的是检索，而不是换更贵的模型：v4-pro 比 flash 慢 3 倍，分数完全相同。
5. **用范围决策收口。** 本地模型服务（LM Studio）会把部分输入输出写入本机日志。我没有继续深挖第三方工具的日志机制，而是明确规定本地模型服务只处理合成数据，并为接入真实数据的模型服务写了验收清单。

6. **单次运行不是证据。** Top-K=8 和 1000/150 分块的「提升」都只来自一次运行；后来发现同一配置的可答题数就能在 41–44 之间波动。于是写了重复运行脚本，`compare` 只有在两边每轮分数的范围不重叠、且每边至少 3 轮时才说「可区分」，并回头撤回了那两个结论。
7. **一串无意义的随机字符也会改答案。** 提示词里每次请求随机的边界标记，在 `temperature=0` 下就能让一道边缘题在完整与不完整之间翻转（约 54% 完整）。改成由服务端密钥对（问题 + 检索分块）做 HMAC 的确定性边界后，相同输入得到相同提示词，同时仍不能被文档作者预测。

## 6. 局限

- 没有生产部署、公开 Demo 或真实用户数据（有一段无声终端演示视频，不含 App 画面，见 `docs/demo/`）；数字来自本地的合成与公开文档数据。
- 质量门只对「bge-m3 + `temperature=0`」配置通过，默认配置不通过；评测题由单人基于文档编写、用子串规则评分；跨文档题仍然失败。
- ACL 只支持 allow 规则；更换 Embedding 模型需要全量重建，重建完成前未重建的文档不可检索（转人工）。
- MCP 是最小的只读适配，没有第三方 SDK 互操作验证，也没有 Agent 循环或写操作。

## 业务价值（待真实数据验证）

不虚构 ROI。上线后需要用真实用户和至少 7 天的运营基线来测量：

- 员工查找资料的时间是否下降；
- 带引用回答的采纳率和“有帮助”反馈率；
- 拒答和 ACL 拒绝能否减少错误信息的传播；
- 文档从更新到可检索的时间；
- 单次问答的 Token 用量与成本。
